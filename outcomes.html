Learning Outcomes

Ethics

Before this class I would look at if the AI works or not and that was pretty much it. In week 3 I learned an AI can work the way it was made and still end up hurting people. We went over three ways this happens: algorithmic bias, calibrated trust, and dual-use. In class we used the Workday lawsuit, the Winters case, and voice cloning scams. For this draft I took those same three ideas and applied them to things from the field I'm going into.

Algorithmic bias is when an AI follows the same rule for everyone but still treats some groups worse. A lot of the time it happens through a proxy variable, which is something that ends up standing in for a trait the AI never asks about.

Banks use AI to flag transactions that look like fraud. The AI never asks where you're from, but it does look at stuff like sending money to other countries, spending in a different place than usual, or having a newer account. Immigrants who send money home to family do all of those things a lot. So the AI could keep freezing their cards even though it's never told anyone's nationality. That's the same idea as the work history gaps in the Workday case, just with money instead of jobs.

The fraud model might still be "working" because it catches real fraud. But if one group gets flagged way more for normal stuff, that's a problem. One fix is to check how often the AI wrongly flags people in different groups, not just how much fraud it catches overall.

I did help desk at my co-op and a lot of tickets were password resets. Some companies are starting to let AI chatbots handle these, so I ran it through the three questions. Can I check it? Not really, because if the chatbot decides someone is who they say they are, there's no person double checking. How bad is it if it's wrong? Really bad, since if it resets the password for the wrong person an attacker now has someone's account. Can it be undone? Not fully. You can lock the account after, but whatever they did or downloaded already happened.

So I'd trust an AI to answer basic stuff like how to connect to the wifi or reset a printer. But I wouldn't let it verify someone's identity on its own. When I did resets we had steps to confirm who the person was, and I think a human should still be part of that.

Dual-use is when a tool made for something good gets used for something bad. In class it was voice cloning. A newer example is chatbots writing phishing emails.

Phishing emails used to be easy to spot because they had bad spelling and weird grammar. Now anyone can have an AI write a clean, professional email that looks like it came from IT or a bank. That makes them a lot harder to catch. But security teams use the same kind of AI to make fake phishing emails for training, so employees can practice spotting them. Same tool, totally different use

Like with voice cloning, I think the companies that make these tools should take some responsibility since this kind of misuse is easy to see coming. But I don't think you can fully stop it, so the defense side matters too, like training people and making it easy to report a sketchy email.

All three of these show up in cybersecurity. Fraud detection, identity checks, and phishing are things I'll actually deal with at work. Before, I would have just asked if the tool works. Now I'd also ask who it might treat unfairly, how much I should trust it, and how someone could use it for something bad.

History

Week 1 showed me that AI goes back much further than ChatGPT. The big pattern I noticed is that rule-based AI, like expert systems, kept breaking outside of what it was built for, so the field switched to learning from data instead. I wanted to see if that same pattern shows up somewhere we didn't talk about in class.

I looked at the history of machine translation, which is getting a computer to translate one language into another. It started in January 1954 with the Georgetown-IBM experiment. They used an IBM 701 to automatically translate more than sixty Russian sentences into English. It worked off a small dictionary and handwritten grammar rules, which is the same "if this, then that" approach as early AI. The researchers said translation could be a solved problem in three to five years, and since it was the Cold War and the US wanted to read Russian documents, the government put a lot of money into it.

It didn't work out. The system did fine on its small set of sentences but struggled once the dictionary got bigger, because real language is messy and the same word can mean different things depending on the sentence. In 1966, the government's ALPAC report found that ten years of research hadn't lived up to what was promised. Machine translation was slower, more expensive, and less accurate than just paying a human, so funding got cut way down. That's basically the same thing the Lighthill Report did to AI in 1973, except it happened to translation seven years earlier.

The comeback followed the same pattern too. Instead of writing more rules, researchers switched to statistical methods that learned from huge amounts of text that was already translated by people. Google Translate used this kind of system for about ten years. Then in 2016 Google switched to a neural network, and in side-by-side tests it cut translation errors by about 60 percent. The next year the transformer came out, and it was actually built to make translation better. That's the same design ChatGPT is built on now.

This connects to the McCarthy essay we read. In my response, I argued that when McCarthy answers people like Searle who say AI is impossible, he isn't really making a philosophy argument about minds, he's making an engineering one about how the system is built. The Georgetown team had that same engineer mindset. They didn't care if the computer actually "understood" Russian, they just wanted it to put out the right English. The problem is they thought that would be easy. Translating well takes a lot of common sense knowledge about the world, like knowing which meaning of a word fits the sentence, and that's the kind of knowledge McCarthy says an AI has to have built in. So their engineering approach made sense, they just way underestimated how much the system needed to know.

What I took from this is that the timeline from Week 1 isn't just something that happened to AI in general. One specific problem went through every stage: the early hype, a winter when the rules couldn't handle the real world, a comeback from learning with data, and then deep learning. It also shows how much a field depends on hype and funding. The Georgetown team promised way too much way too fast, and when it didn't happen, the money disappeared for decades. With how much hype there is around AI right now, I think that's worth remembering.

Search

Weeks 4 and 5 were about how an AI finds a path from where it starts to a goal, and what changes when someone is fighting back. Everything in class used robots like Scout and games like chess, so I applied both kinds of search to cybersecurity instead.

BloodHound is a tool that maps out a company's Active Directory, which is the system that controls who has access to what on a Windows network. It treats the network like a graph. Users, computers, and groups are the nodes, and things like "is a member of" or "is an admin on" are the edges.

In search terms, the initial state is one user account an attacker got into, and the goal test is whether that account has Domain Admin access. The transition model is following an edge, like using an admin login on a computer to get to the next account, and the path cost is the number of hops.

BloodHound's "shortest path to Domain Admins" uses breadth-first search, going from both ends at the same time. BFS makes sense here because every hop costs the same, so the first path BFS finds is the one with the fewest steps.

The interesting part is that both attackers and defenders use it. Attackers use it to find the fastest way to take over a network. Defenders run it on their own network to find those paths first and cut them off by removing permissions people don't need.

BloodHound assumes the network just sits there. In real life the IT team fights back, so I made my own game for that. An attacker already got past the firewall and the defender is trying to stop them. They take turns. The defender patches one server and the attacker takes over one unpatched server connected to something they already own. The game goes two rounds and the score is the total value of what the attacker owns.

The network has Web (worth 2) leading to DB (worth 5), and Mail (worth 1) leading to HR (worth 3). The attacker is MAX and wants a high score. The defender is MIN and wants a low score.

Using minimax and working from the bottom of the game tree up, patching Web first holds the attacker to 1. Patching Mail lets them get 2, and patching DB or HR lets them get 3. So the best move is patching Web. Alpha-beta pruning gets the same answer faster. Once the Web branch gives a 1, the defender knows it can get at least that. In the DB and HR branches, the first attacker move already scores 2 or more, so the rest of those branches get skipped.

What surprised me is that the obvious move is to protect DB since it's worth the most, but that's actually worse. Patching Web blocks the only way to DB and leaves the defender a free move to shut down the other side. In security that's called a choke point.

My game only works because the network is tiny, so I could search all the way to the end of the game and get an exact score. A real company has hundreds of servers, so the tree would be way too big to search that far. In that case you'd have to stop early and use a heuristic evaluation function to guess how good a position is. For this game a simple one could be adding up the value of every server the attacker can still reach. It wouldn't be perfect, but it would be fast enough to actually use.

Regular search works when nothing is fighting back, like mapping out paths in BloodHound. Adversarial search is closer to how security actually works since the attacker is always reacting to what you do. Both showed me the best answer isn't always the obvious one, which is why it helps to have the computer check every option.
